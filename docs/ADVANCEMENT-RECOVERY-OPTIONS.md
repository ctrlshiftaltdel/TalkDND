# 单职业成长：迁移与显式恢复备选方案

状态：供所有者决策的分析，不是实现、批准、默认选择或安全保证。基线为 `2dbdb1018d20957cfbde7ca2801a32b7ac913579`；仅依据公开代码及 [成长设计](superpowers/specs/2026-11-10-character-advancement-design.md) §3–5、[安全审计](ADVANCEMENT-SAFETY-AUDIT.md) 和 [锁调查](CHECKPOINT-LOCK-INVESTIGATION.md)。未读取真实存档、书籍或秘密。下文“应”为候选方案的必要机制，不是现有能力。数据丢失风险须由 Master 和独立 Reviewer 在未来实现中复核，所有者决定协议。

## 1. 已批准边界和事实

未来 schema 11，9/10 自动迁移；迁前完整备份，保留手改和历史未知；持久操作标识与阶段记录，失败停止、显式恢复；预览不写，提交重新验证；活动遭遇允许预览但不提交。具体存储、锁、恢复、遭遇识别、备份保留均未决定。无论哪种选项，缺记录不等于历史未选；不从当前特性倒推机会。不能以本报告或单文件原子写证明任何真实存档受保护。

基线静态事实：`progress::level_up` 可先追加 `rolls.log`，结构化路径经 `charsheet::commit` 顺序写 `sheets/<id>.yaml`、party state、`Characters/<name>.md`，之后里程碑进度、session 日志，外层 `audit::after_command` 刷新完整性；旧 Markdown 路径不同，多角色顺序执行且前者失败不回滚。`migrate::ensure` 现为 schema 10，9→10 避免重写 dirty sheet；`Cmd::LevelUp` 未直接确保主 schema。`migrate::backup_save` 排除 `_backups`、`.cache`、`.talkdnd` 且可能跳过特殊项；checkpoint 的复制又有不同排除和特殊文件拒绝。它们均不能作为未来完整备份的证明。详见安全审计的各函数与测试定位。

## 2. schema 11 的两种记录结构（未选定）

| 对照 | A：角色 YAML 内扩展选择记录 | B：独立、版本化选择 sidecar，以角色稳定身份关联 |
|---|---|---|
| 9/10 迁移 | 不为历史猜选择；dirty、注释和未知键不可被序列化重写吞掉；无法无损修改则停止，留原字节与人工处理 | 原角色字节可保持；创建新 sidecar 记历史未知，但仍须备份、阶段记录、检测名称碰撞与孤儿关联 |
| 旧 Markdown、缺 sheet | 不强制生成 sheet 或伪造历史；需要有损转换时停止待决定 | 无 sheet 也须可靠身份；重命名、同名和删除造成关联歧义时停止，不按名称猜测 |
| 来源、版别、重复 | 每条记录候选包括机会 ID、角色 ID、规则集、来源和身份、验证状态及确认依据；重复专长需要区分机会与选择实例，不能仅按名字去重 | 同左，但还需原子性以外的跨文件关联验证；手工编辑和复制 sidecar 可能制造重复或漂移 |
| 风险 | 旧读写器可能丢新字段或注释；无损文本编辑复杂 | 易被旧程序忽略、遗漏或复制到错误角色；独立文件不能自动绑定角色状态 |

机会身份、可重复条件、身份消歧和补录形式均需规则与所有者决定。未来 schema 被部分旧入口拒绝不等于全局保护：旧版可能不检查主 schema 就写 Markdown、party 或进度。迁移后停止旧版写入，逐发布版本逐入口合成审计；提示和版本标识不能阻止旧二进制或外部编辑。损坏/未来 schema、无法解析的未知字段、历史缺口和授权不明均不可当作空记录。

## 3. 两套完整备份与恢复协议候选

两套均要求**完整备份 + 持久操作 ID/阶段记录 + 失败停止、显式恢复**；二者只是假设可实现的协议，不承诺多文件原子性。所谓完整：覆盖执行前存档全部用户数据，包括角色、party、进度、所有日志、完整性清单、遭遇、手改、未知文件和既有备份；备份本身及操作工作目录为避免递归可置于存档外并单独列示，锁文件只作为控制元数据排除，排除集合须明确并由用户确认。若历史备份、权限、ACL、时间戳、硬链接、稀疏文件、符号链接、设备、FIFO、套接字、挂载点等无法安全复制或验证，须拒绝开始并说明；不能静默略过、跟随链接逃出根目录或在恢复时写入外部路径。平台元数据语义和可移植性 UNKNOWN，不能保证硬件或文件系统持久性。

共同前提：对规范化的存档身份取得覆盖所有**协作**写者的锁，验证身份、授权、预览输入及内容版本；建立唯一不可复用操作 ID，确保备份位置独占创建，不依赖秒级时间戳。备份清单记录路径、类型、大小、摘要和支持的元数据，校验副本与来源；同步文件及目录和阶段记录，并明确文件系统/平台上持久化语义是否可用，不可确认则停止或明确不支持。记录不得包含日志正文、秘密或书籍正文；备份本身敏感，需隔离访问权限和保留策略，磁盘空间估算不等于写成功。非协作修改即使发生在校验前后也可能逃逸检测，哈希不是锁或真实性保证。

| 阶段 | C：原位逐文件提交 + 前像备份 | D：暂存完整候选树 + 逐文件发布 |
|---|---|---|
| 准备 | 申请锁，确认无未结束操作；记录 ID 和 `preparing` | 同左，并在同一受控文件系统创建独立暂存空间 |
| 备份 | 完整复制、校验、持久化后记录 `backup_verified`；失败/空间不足时不开始目标写入，保留不完整产物供人工检查 | 同左；额外确认可容纳备份及暂存，空间不足不发布 |
| 准备改动 | 计算每文件前像/目标摘要、写入顺序与意图，持久记录后才逐文件替换 | 从已验证前像生成候选并校验；记录候选清单和每文件前像/目标，不能以目录改名假称多文件事务 |
| 发布 | 每个文件先持久记录 intent，验证当前与前像一致，再替换并同步，记录完成；包括 YAML、Markdown、party、进度 | 同样逐文件核验并发布候选；候选过期或有冲突即停止，暂存副本不能覆盖新手改 |
| 日志和完整性 | 日志独立按操作 ID 去重；追加前后记录意图、偏移/摘要并核验，避免截断后续记录。最后核验完整性清单，仅接受已确认工具写入，不洗掉原有 dirty 状态 | 同左；不能简单从暂存树替换实际追加日志或清单 |
| 结束 | 验证完整关系、记录完成并同步；清理须另外明确批准的保留策略 | 同左；暂存与备份清理不属于成功的必要证明，不能提前删除唯一可恢复副本 |

对任意阶段崩溃、写满、短写、同步失败、重命名成功但记录尚未落盘，下一次必须识别不确定状态并禁止继续普通写入；检查实际内容与前像/目标/记录，不能仅信阶段标签。不存在有效完整备份或记录损坏时禁止自动恢复，隔离并请求人工从外部副本恢复；已有部分写入时明确指出可能不一致，不能声称已回滚。每次恢复也须先保护恢复时当前树（包括之后手改与日志），检查备份完整性及目标身份，对差异展示并由人选择；不能直接整树覆盖。遇不匹配、日志中有后续追加、重复 ID 或不可判定状态停止，保存两份证据并要求人工合并；不得删除后续日志。显式恢复可候选为回滚到前像或核验后继续完成，但每次选择均需确认、独立记录、逐步同步，恢复再次中断也走同样流程；若内容既非预期前像也非目标则不自动判定。重试凭 ID 与已验证内容判别，不能重复加属性、XP、资源或日志；无法确定是否已追加时停下而非重放。

C 优点是额外空间较少、写入路径直观；缺点是中间状态更久暴露，手动合并困难。D 可在发布前检查完整候选，但需要更多空间、候选可能过期，发布仍有部分状态、恢复与日志冲突；都不适用无法取得完整备份、无法确认锁域/文件系统持久性或无法隔离外部写者的环境。磁盘损坏、断电时设备谎报同步、备份与原件同介质丢失、非协作编辑/旧程序、跨设备或网络文件系统锁语义，以及恶意篡改均不受保证；需要外部独立备份和环境验证，仍非绝对保证。

## 4. 锁域、预览及未决风险

当前 checkpoint `.talkdnd.lock` 只协调 checkpoint，自带超时移除；完整性 `.talkdnd.integrity.lock` 是另一把文件锁，仅保护清单读改写，不能保护其他存档写入。#264 的首次锁失败根因 UNKNOWN；[调查](CHECKPOINT-LOCK-INVESTIGATION.md) 的后续通过不证明安全。未来须先盘点 `talkdnd`、`combat-sim`、迁移、checkpoint、日志与所有写路径，定义共享锁域、顺序、锁文件身份稳定性、死锁/崩溃和超时处理；不能拆掉被持有的锁 inode，也不能把过期时间当持有者死亡证明。#264 未解决时不得把现有锁当安全基底。锁不约束编辑器、旧版本或另一个不遵守协议的进程；即使逐文件复核，检查与写入间仍有竞态。最坏后果是覆盖玩家手改或丢失 session/骰子日志，角色 YAML、Markdown、party、XP、完整性和遭遇各处不一致，后续错误基线掩盖损失。

预览须绑定角色、party、进度、日志相关状态、规则集及实际授权内容、完整性和遭遇的身份/摘要，并在持锁下重新核验；来源、规则版本、许可状态或任何输入变化须重新预览。仅哈希已知路径不能发现新增文件或检查后非协作修改；枚举清单及版本也非全局快照。`EncounterState` 的命名/显式/外部路径、损坏文件、多遭遇和可能滞后的 `outcome` 使活动识别 UNKNOWN；不能以文件存在或 outcome 非空单独证明结束。所有者需确定发现范围、歧义和不可信状态如何处理；已批准边界是活动时不提交，不能发明判定算法。

## 6. 提交所有者的问题与条件推荐

1. 记录放角色 YAML（A）还是 sidecar（B）？建议**有条件考虑 B**，前提是稳定身份、孤儿检测和关联恢复能经合成验证；否则 A 的无损编辑或其他设计须另审。如何补录历史、标识机会/可重复选择需单独决定。
2. 原位 C 还是暂存 D？建议**有条件考虑 D**，前提是空间充足、同设备语义和逐文件发布/恢复经故障测试；D 不更原子，空间不足时不能擅自降级 C。完整备份覆盖和排除、特殊文件、元数据、同步、保留期、日志去重和显式回滚/继续的授权均需决定。
3. 哪些进程、操作与平台加入共享锁域，锁顺序和无法确认持有者时如何处置？#264 根因须继续调查，安全模型变化需所有者授权；旧程序和外部编辑仍无法强制。
4. 如何识别活动遭遇、处理不可发现/损坏/多状态，以及旧版禁写如何告知和逐入口审计？规则语义、授权来源和未知前提确认权限须另决；不把本分析作为实现授权。

在选项批准前不实施迁移；未来实现 PR 的 Master 与独立 Reviewer 应逐阶段核查上述故障矩阵、原始 dirty 与后续日志的保全、#264 处置及所有者选择记录。回退本文为普通文档 revert，不触及存档。
