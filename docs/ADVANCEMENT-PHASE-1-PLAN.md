### 已批准边界（本计划只承接，不缩窄、不新增）

1. 主存档 **schema 11**，**自动迁移 9/10→11**；迁移前**完整备份**，且完整备份**包含玩家既有用户备份**。
2. 控制元数据（锁文件、操作前快照、恢复工作记录）**单独保留**，不并入用户数据的完整备份；保留期与清理责任仍未定，未定前不得假定可删除或可排除。
3. 仅支持**本地常见文件系统**；网络盘、FUSE、同步目录不支持，且**强制准入门未实现**——不得声称这些位置已被拒绝，跨主机/网络互斥仍 `UNKNOWN`。
4. **所有相关新版本写者被覆盖之前，成长提交入口不启用**；未接入的入口必须在同一存档上拒绝写入或声明只读（OD-2）。只读预览/诊断可以先上线。
5. **Windows 本地提交不支持**（平台无目录 `fsync`：`init` 返回 `state_published_not_durable`，可写谓词与提交一律拒绝）；不得把“`init` 建了文件”当成可提交。
6. **#264 未解决**；现有 checkpoint 锁不是 OS 锁，旧二进制、外部编辑器与不遵守协议的进程不受约束。
7. **不承诺多文件原子性**；不承诺检测共同复制“角色 + sidecar”或整档重放/回滚，也不承诺识别保留标识的整盘镜像。
8. **预览只读**；**活动遭遇只预览、不提交**；损坏、歧义或无法可靠判断的遭遇同样拒绝提交。
9. **仅自动更新来源与派生关系可可靠确定的数值**；不确定的保留并提示 DM，不覆盖手改、不静默重生成。
10. 首阶段全部验收后**暂停**，不进入全量专长自动化。

### Phase 1 — 写者覆盖与 D 前置

- 阶段目标：任何相关新版本写入入口都不再能“静默写入且不持锁”；D 流程能走到“候选已验证、未发布”。

### Phase 2 — 发布、日志/幂等与显式恢复

- 阶段目标：发布、日志/完整性、幂等与显式恢复在合成故障注入下符合已批准边界；内层锁未决时提交路径不接入。

### Phase 3 — sidecar 入籍与 9/10→11 迁移

- 阶段目标：合成 fixture 上能完成 schema 11 的 sidecar 入籍与 9/10→11 自动迁移，且手改与未知历史不被覆盖。
- 交付：`ADV-P1-5`。

### Phase 4 — 预览、选择、提交与可靠派生数值

- 阶段目标：预览只读、选择显式、提交重新验证并拒绝过期/并发变化；只有可靠派生数值自动更新。
- 交付：`ADV-P1-6`、`ADV-P1-7`。
- 出口条件：① 预览不创建、不锁定、不写任何文件，并输出 `consistency: unverified` 与 `write_capability`；② 绑定变化、未提供 `preview_id`、并发手改一律拒绝并要求重新预览；③ 可可靠派生的数值恰好更新一次且不覆盖手改，其余保留并提示 DM；④ 活动遭遇只预览——**遭遇识别算法未决前该出口条件无法判定通过**，不得自行发明算法。

### Phase 5 — 端到端、跨平台与故障注入收口

- 阶段目标：端到端、跨平台与故障注入有实测证据，未跑项一律标 `NOT_RUN`。
- 交付：`ADV-P1-8`（并汇入 `ADV-P1-9` 的独立结论）。
- 出口条件：① 三平台 CI 的合成套件结果按平台分别记录；② 故障注入矩阵逐项有 `PASS` / `FAIL` / `NOT_RUN`，没有把未跑折算为通过；③ 端到端合成与四规则集隔离有证据；④ 网络盘/FUSE/同步目录、跨主机互斥、掉电持久性、整盘镜像/重放与共同复制检测全部保持 `NOT_RUN` / `UNKNOWN`，并在报告里列为已知限制。

## 只能由实现后实验证明的结论（全部 `NOT_RUN`）

下表列出**不能**靠设计、静态阅读或既有测试通过来证明的结论。实现前它们一律是 `NOT_RUN`；实现后也只有真实执行并绑定 head 的证据才能改变状态。

| 结论 | 需要的实验 | 当前状态 |
|---|---|---|
| 两个协作写者同时提交时恰有一方成功、失败方不写目标 | 多进程竞争（T1），三平台 | `NOT_RUN` |

| 崩溃后不自动续跑，`active`/`in_doubt` 拒绝普通写入 | 分阶段 kill（T4a/T4e） | `NOT_RUN` |
| state 原子替换与目录持久窗口的真实行为 | 掉电/同步失败注入（T4b/T5i） | `NOT_RUN` |

## 维护规则

- 本文件只经任务分支 + PR 修改；不在会话里口头改计划而不落文件。
- **任务状态、负责人、完成度与“下一个要做什么”只写在 GitHub Issues**；本文件不新增状态列、不复制 Issue 状态、不建第二套台账。若某块需要状态，去看对应 Issue。
- 新任务先作为 Issue 登记（任务包字段与证据矩阵按 [kit/orchestration.md](../kit/orchestration.md) 4.1），再回到本文件登记“顺序、依赖、建议允许路径与 AC”；不先在本文件造任务。
- 顺序调整必须同时更新「阶段」的出口条件与相关任务块的 `Depends on`，并说明依赖是否仍满足；不得只改顺序不改依赖。
- 任务块粒度过粗（一个块含多个可独立验收的结果，或 AC 无法逐条勾验）时先拆块再登记 Issue，不把粗块直接派发。
- 未运行、被阻塞或无法判定的实验一律写 `NOT_RUN` / `BLOCKED` / `UNKNOWN`；不得因为“设计上应该如此”而写成通过，也不得把未实现能力写成已完成。
- 与 `docs/PLAN.md` 的设计目标冲突时，停下对齐并以设计目标为准，不在两处各写一套；需要改变范围、目标、规则支持或一项用户决定时，按 LIVING CHARTER 在同一 PR 更新 `docs/PROJECT-CHARTER.md`。
- 本文件不写日期与排期；任何“什么时候做完”的信息不属于计划文件。
