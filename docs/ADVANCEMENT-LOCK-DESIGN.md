# 成长协作锁域与恢复协议（设计）

状态：**仅设计**。本文不实现锁、不改代码、不迁移存档、不写 sidecar、不改变已批准的 B/D/Q 或备份/恢复边界。代码事实基线 `cc7876077d705598eed7f08ad7b365168efccfdc`；合成测试与故障注入**全部未执行**。依据 [身份契约](ADVANCEMENT-IDENTITY-CONTRACT.md) §3–§6、[恢复选项](ADVANCEMENT-RECOVERY-OPTIONS.md)、[安全审计](ADVANCEMENT-SAFETY-AUDIT.md)、[锁调查](CHECKPOINT-LOCK-INVESTIGATION.md) 与[成长设计](superpowers/specs/2026-11-10-character-advancement-design.md)。只读公开源码、测试与既有文档；未读取真实存档、书籍、DM 秘密。

标记约定：**事实**指能从当前公开代码/测试直接读出的行为；**推断**指由静态事实推出、未实测的后果；**UNKNOWN** 指本次不能判定，不等于安全。现有测试通过**不是**锁安全证据；#264 未解决前，任何“现有锁已够用”的结论都不成立。

## 0. 本文件回答什么、不回答什么

回答：新版本成长提交会碰哪些写入对象；它们今天受哪把锁保护、按什么顺序写；协作锁应当怎样定义身份、作用域、获取顺序、持有与失效；它嵌进已批准的 D 流程后各阶段何时持锁、失败怎么停、哪些动作可重试；Linux/Windows/macOS 上哪些结论能用合成测试判定。

不回答/不承诺：不承诺多文件原子性、不承诺消除 TOCTOU、不承诺约束旧二进制/外部编辑器/不遵守协议的进程、不承诺跨网络文件系统语义、不宣布 #264 已解决、不给出实现排期、不改变任何既有安全承诺。

### 1.2 现有两把锁的机制（逐条事实）

**checkpoint 锁 `.talkdnd.lock`**（`tools/talkdnd/src/checkpoint.rs`）：

1. 获取 = `OpenOptions::create_new(true)` 创建文件，写入本进程 PID（`Lock::acquire`）。**事实**：不持有任何 OS 文件锁。
2. 冲突 = 文件已存在；若 `stale()` 判定（mtime 距今 ≥ `LOCK_STALE_SECS = 600` 秒）则 `remove_file` 后重试一次（`stolen` 只允许抢一次），否则报“另一个 checkpoint 操作正在进行”。
3. 释放 = `Drop` 里 `remove_file(&self.path)`。**事实**：无归属校验、无 inode 校验。
4. 推论（**推断**，未实测）：(a) 进程被 `SIGKILL` 后锁文件留在原处，最长 600 秒内所有 checkpoint 操作被拒，之后任意后来者删除并接管；(b) 若 A 的快照超过 600 秒（大存档复制），B 会删掉 A 的锁并开工，两个写者同时操作同一存档；(c) 若 B 已接管并新建锁文件，A 结束时 `Drop` 会删除 **B 的** 锁文件，第三个写者因此可以进入；(d) `stale` 只看 mtime，不看持有者是否存活，也不看进程 PID——PID 只被写入、从未被读取。**这不是安全基底。**

**完整性锁 `.talkdnd.integrity.lock`**（`tools/combat-sim/src/integrity.rs`）：

1. 获取 = `OpenOptions::create(true).truncate(false).write(true)` 打开固定路径，再 `File::lock()`（Rust 标准库文件锁；Unix 为 `flock`，Windows 为 `LockFileEx`）。**事实**：阻塞等待，无超时；同一进程再次获取会自锁死（源码注释明确要求用 `*_locked` 变体）。
2. 释放 = 句柄 `Drop` 或进程退出，由 OS 释放。**事实**：崩溃不会留下“陈旧锁”；锁文件永不删除、从不参与完整性指纹。
3. 覆盖范围 = 只有 `integrity.yaml` 的读改写。**事实**：`audit::after_command`、`integrity::ensure/changes/after_write`、`migrate::carry_dirty_flags_guarded`、`checkpoint::restore_rebaseline` 在同一把锁下更新清单。

**顺序事实**：`checkpoint.rs` 模块注释声明 checkpoint 锁先、完整性锁后，“never the reverse”；`restore_inner` 全程持 checkpoint 锁，并在其中调用 `migrate::ensure`（内部会取完整性锁）与 `restore_rebaseline`。**事实**：这是当前代码里唯一成文的锁序。除此之外没有全序表，也没有进程内的“已持有集合”检查。

**普通命令的写序列（无保存级锁）**：`lib.rs::run` = 解析 →（多数命令）`integrity::snapshot`（无锁）→ `dispatch`（真正写入：`charsheet::commit`、`Progress::store`、`save::append` …）→ `audit::after_command`（此时才取完整性锁）。**事实**：写与清单更新之间没有互斥；`snapshot`/`dispatch`/`audit` 三段之间，另一个进程可以完整插入。

### 1.3 现有锁文件在备份/回滚中的位置（事实与风险）

- `checkpoint::copy_tree` 只跳过 `.talkdnd.lock`；`integrity::LOCK`（`.talkdnd.integrity.lock`）会被复制进备份/回滚镜像。
- `checkpoint::remove_extras` 同时跳过 `.talkdnd.lock` 与 `integrity::LOCK`（不回删）。
- 镜像回滚用 `copy_tree(&backup, save)` 写回；`std::fs::copy` 对已存在的目标是**截断写同一 inode**，不是替换 inode，但会**改写**该锁文件的字节内容。**推断**：若回滚发生时另一个进程正持有该 inode 的排他锁，OS 锁仍然有效，但基于文件内容的持有者记录会被污染；任何“读记录判断持有者”的协议都必须在获取锁之后才读，且容忍损坏记录。
- `migrate::copy_tree` 不跳过任何锁文件，备份里会出现这些锁文件的副本。**推断**：用它恢复/复制时可能把锁文件带到新位置，`(路径, inode)` 级别的锁身份不能因此被当成同一把锁。

### 1.4 现有测试能证明什么（不能证明锁安全）

| 测试入口（事实） | 实际覆盖 | 为什么不是锁安全证据 |
|---|---|---|
| `tools/talkdnd/tests/checkpoint.rs::a_held_lock_fails_the_second_call_and_a_retry_after_release_works` | 手工写入锁文件后，同一进程的快照/恢复被拒；删除后恢复 | 只验证“文件存在即拒绝”，不验证真实竞争、进程死亡或锁文件被替换 |
| `tools/talkdnd/tests/checkpoint.rs::concurrent_snapshots_exactly_one_wins` | **同进程两个线程**竞争一次快照 | 没有第二个进程；不覆盖 OS 锁、`Drop` 删除他人锁、stale 抢占 |
| `tools/talkdnd/tests/checkpoint.rs::restore_rebaseline_keeps_a_concurrent_writers_fingerprints`、`rollback_keeps_the_integrity_lock_a_concurrent_writer_holds` | 恢复/回滚期间清单锁与另一个“写者”的指纹 | 写者是测试自己构造的句柄/子进程，且 `rollback...` 正是 #264 首次失败点；#264 未解决 |
| `tools/combat-sim/src/integrity.rs` 测试（如清单锁失败不泄漏锁） | 清单读改写的互斥与错误路径 | 只覆盖清单这一把锁，不覆盖角色/party/进度/日志 |

## 2. 协作锁协议（AC-2）

### 2.1 目标与不变式

协作锁只负责一件事：**让所有遵守本协议的新版本写者在同一个存档上串行执行“可能改变存档内容”的操作，并让崩溃/接管有可判定的状态**。它不是认证、不是防篡改、不约束不遵守协议的进程。

| ID | 不变式 |
|---|---|
| I1 | 一个存档同一时刻最多一个遵守协议的持有者处于“可写阶段”。 |
| I2 | 锁文件一旦存在就**永不删除、永不 rename 覆盖**；只在同一 inode 上原地改写记录。 |
| I3 | 锁文件路径指向的 inode 在持有期间不得改变；检测到改变即中止，不继续写。 |
| I4 | 持有者存活由 **OS 锁**判定；记录里的时间/心跳/pid **不能**作为抢占依据。 |
| I5 | 获取失败一律失败关闭：不降级、不失锁重试为“只读提交”、不吞掉只报警。 |
| I6 | 锁只覆盖一个存档；跨存档不做全局互斥（不同存档可并行）。 |
| I7 | 锁不改变任何既有写入语义；既有内层锁（完整性、checkpoint）原样保留并仍按自己的规则工作。 |
| I8 | 任何阶段的失败都必须留下可定位的（操作 ID、阶段、备份位置、已写/未写）记录，且不得删除唯一可恢复副本。 |

### 2.2 锁身份与位置

- **路径**：`Saves/<slot>/.talkdnd.advancement.lock`（存档根目录，与 `.talkdnd.integrity.lock` 同级）。
- **作用域**：该存档目录下的全部内容文件，加上**本次操作**在存档外创建的备份目录与候选暂存目录（由操作记录里的绝对/相对路径引用，仍受同一把锁保护）。不含 `Rules/`、`Adventures/`、其它存档。
- **锁身份**（三层，缺一不可）：
  1. **存档身份**：`canonicalize` 后的存档真实路径（拒绝非目录、拒绝解析后逃出 `Saves/` 的路径）。
  2. **锁文件身份**：打开句柄的文件标识（Unix：`dev`+`ino`；Windows：文件索引卷序列/文件 ID，或等价的可复核标识）。路径 → inode 的映射在每次获取、每次阶段切换前复核。
  3. **持有令牌**：每次获取生成随机 `owner_id`（非秘密、够长以排除碰撞），写入记录；同一进程内的后续调用以“已持有句柄”传递该令牌，不重新获取。
- **记录内容**（设计字段，不是已实现格式）：`schema`、`protocol_version`、`save_path`（相对仓库根的路径，避免写入个人绝对路径）、`save_id`（首次创建时生成的随机标识，仅本机存档内唯一）、`owner_id`、`pid`、`host_label`（可配置，默认空）、`tool`+`version`、`mode`（`advance-preview` / `advance-commit` / `recovery` / `checkpoint` / `migrate`）、`operation_id`、`stage`、`state`（`held` / `released` / `complete` / `failed` / `in_doubt`）、`acquired_at`、`heartbeat_at`、`deadline_hint`、`preview_id`、`notes`。记录**只**写本地、不写日志正文、不写角色内容、不写秘密。
- **不变量**：记录是诊断信息，不是锁本身。获取顺序必须是“先拿到 OS 锁，再读/写记录”；**任何**基于记录内容（时间、pid、state）的抢占都不允许。

### 2.3 获取、释放与重入

获取（每次可写操作入口，包括 preview 的只读一致性窗口）：

1. 解析并规范化存档路径；不满足则拒绝，不创建锁文件。
2. 打开锁路径：`create(true).truncate(false).read(true).write(true)`。**禁止** `create_new`（它无法区分“有人持有”与“上次崩溃”）。
3. 用 `try_lock` 在**有界 deadline** 内轮询（默认 5 秒，可由显式参数覆盖；不写成常量承诺，见 §5 ED-3）。deadline 到期即读取记录并失败，错误里带脱敏的持有者信息与“稍后重试/人工确认”指引。
4. 取得 OS 锁后复核“路径 → 同一文件标识”。若路径已被删除或替换：释放、重新打开（有限次数），仍不一致则失败并报告“锁文件被替换”。
5. 读取旧记录（用于发现未结束操作），然后**在原地**截断+写入新记录并 `sync_all`；写入后从同一句柄读回比对 `owner_id`。读回不一致即释放并失败。
6. 若旧记录 `state` 不属于 `{released, complete}`（即疑似未结束操作），**不自动接管写入**：进入 §2.6 的存疑门。
7. 通过后才进入命令的阶段机。

释放：

1. 先写最终记录（`released` / `complete` / `failed` + 最后阶段 + 心跳时间），`sync_all`。
2. 再释放 OS 锁（drop 句柄）。
3. **永不** `remove_file` 锁文件；**永不**在释放时判断“路径还是不是我”——若路径已被替换，直接记录并释放，不改动替换后的文件。

重入与顺序：

- **总序**：`SAVE（协作锁）` → `checkpoint .talkdnd.lock` → `integrity .talkdnd.integrity.lock`。任何反向获取都算协议违规（实现在进程内维护“已持有集合”并直接报错，不依赖死锁超时）。
- 同一进程同一存档最多持有一个 `SAVE` 句柄；需要嵌套的步骤接收该句柄（`*_locked` 风格），不重新打开。
- 子进程/子命令不继承锁，也不允许“父进程持锁、子进程写”。需要跨进程完成的工作必须在释放后由子命令重新获取（`checkpoint`/`migrate` 属于此类）。
- 现有 checkpoint 代码路径（只取自己的锁）在实现接入前仍是“旧写者”；接入后 checkpoint 也必须先取 `SAVE`，否则总序不成立。

### 2.4 超时、租约与陈旧持有者

- **持有不是租约**：本设计**不**用 TTL 判定持有者死亡，**不**因超时删锁、改名、重命名或“接管”。理由：现有 checkpoint 锁的 600 秒抢占正是同类风险的来源；活持有者超时被抢会产生两个写者。
- **获取有 deadline**：等待方在 deadline 后失败，不无限阻塞（与完整性锁的阻塞语义不同；新锁不能用完整性锁当作获取点）。
- **心跳仅用于诊断与人工判断**：在各阶段切换、长复制前后、每个文件发布前后更新 `heartbeat_at`。心跳陈旧且 OS 锁可用时，获取会**正常成功**（因为 OS 已释放），并把旧记录原样报告出来，进入存疑门——不需要“抢”。
- **人工强制**：只在项目所有者/操作者明确要求时提供 `--force-release` 一类动作，且必须写清目标操作 ID、理由、证据位置；它只能清理**记录状态**或提示人工删除锁文件，不能解除另一个进程持有的 OS 锁（OS 层面做不到），因此绝不能宣称“已解锁”。

### 2.5 崩溃、被替换与平台原语

- **崩溃/被杀**：OS 释放锁；记录留在 `held` 的旧阶段。下一次获取成功，但存疑门会拦下普通写入，要求显式恢复决定（§2.6）。**事实**：这是现有完整性锁已经具备的模型；checkpoint 锁不具备。
- **锁文件被替换/删除**（外部进程、旧版本、清理脚本、备份工具）：
  - 持有者在每个阶段边界、每个文件发布前复核路径→文件标识；不一致立即中止，不再写任何目标文件，记录“锁身份已改变”，保留备份与候选。
  - 两个进程可能因此各持一个不同 inode 的锁——**协议无法阻止**，只能检测并报告。此时任何一方都不应继续发布，因为无法证明另一方的状态。
  - 释放时绝不删除路径（I2），避免“A 释放时删掉 B 的锁”。
- **平台原语**（**事实**：现有代码已用 `std::fs::File::lock` / `try_lock`；语义按平台由标准库映射）：
  - Linux：`flock` 语义，advisory，按打开文件描述；同进程二次打开会自阻。本地 ext4/xfs/btrfs 的行为需实测；NFS/FUSE/网络盘**UNKNOWN**。
  - macOS：`flock`，advisory；APFS 本地盘需实测；网络卷/云同步目录**UNKNOWN**。
  - Windows：`LockFileEx`（字节区锁，强制性更强）；**推断（未在本项目实测）**：标准库默认共享读写与删除，另一个进程可能仍能删除/重命名锁路径，因此“锁文件被替换”的检测不能依赖 OS 拒绝；共享模式、杀毒软件、OneDrive 同步、网络盘的语义**UNKNOWN**，须由实现任务用 T2/T5/T11 实测确认。
  - **能力探测**（必须在写任何目标文件之前）：在存档目录内创建一次性探针文件，取锁后用第二个句柄确认被拒，再释放并删除探针；同一进程探针只证明 API 可用，**不证明跨主机互斥**。探测失败、探针无法删除、目录不可写、出现意外错误 → 失败关闭，错误中说明平台/文件系统与所需人工动作。
  - **不支持时的策略**：不做降级（不退回 `create_new`、不退回“只读提交”、不静默继续）；把该存档标记为“当前平台不支持协作提交”，只允许预览/只读诊断。是否允许所有者显式绕过，见 §5 OD-1/OD-6。

### 2.6 存疑门（in-doubt gate）

获取成功后按旧记录与操作记录判定：

| 旧记录 | 判定 | 动作 |
|---|---|---|
| 无记录 / `released` / `complete` | 干净 | 正常开始新操作 |
| `failed` 且操作记录显示“未发布任何目标文件” | 上次失败在发布前 | 允许普通写入，但先在输出中报告上次操作 ID 与备份位置 |
| `held` / `in_doubt`，或 `failed` 但已发布部分文件 | 未结束操作 | **拒绝普通写入**；只允许显式的检查与恢复命令；列出操作 ID、阶段、备份、已写/未写结论（结论不明就写不明） |
| 记录无法解析/为空但文件存在 | 状态未知 | 视为未结束操作；不猜测、不删除、不覆盖 |

### 2.7 与现有锁共存、以及锁域之外的写者

- **共存**：`SAVE` 是最外层；checkpoint 锁与完整性锁保持原语义，继续按 §1.2 工作。`SAVE` 不取代它们，也不改变 `integrity` 的“清单读改写加锁”承诺。迁移/恢复路径必须把两把旧锁都当作内层锁，并在取 `SAVE` 之后才取。
- **必须先修掉的旧行为**（属于后续实现任务，不是本任务）：checkpoint `Drop` 无条件删除锁文件；`stale()` 按 mtime 抢占；备份/回滚复制锁文件；`migrate::backup_save` 静默跳过特殊文件。这些行为与 I2/I3/I4 直接冲突。**在修掉之前，新锁只能约束遵守新协议的写者，不能修复 checkpoint 自身的竞争。**
- **不受约束的写者（明确列出，不假装能管）**：旧版本 `talkdnd`/`combat-sim` 二进制、外部编辑器、脚本、同步客户端、杀毒软件、备份工具、其它机器上的客户端（网络盘）、PDF 转换进程、手工 `git`/复制粘贴。
- **当前版本的 `combat-sim` 也还不在锁域内**：它的遭遇/party 写路径不取 `SAVE`。因此在新版本把它接入之前，提交流程必须把“可能的遭遇写入”当作并发风险处理（活动遭遇只预览、不提交；检出变化即停），而不是假设它已被锁住。
- **残余 TOCTOU（无法消除）**：即使每个文件在 rename 前复核前像，检查与 rename 之间仍有窗口；攻击者或非协作编辑器可以在窗口内写入并被覆盖。**只能**把窗口压到最小、记录复核值、失败时说明“可能已覆盖某次外部写入”，绝不承诺消除。**#264 未解决期间，这条边界同样适用于现有 checkpoint/完整性锁。**
- **#264**：本设计不解释 `WouldBlock` 首次失败，也不修复它。新锁的实现必须提供诊断模式（记录当时锁 inode、进程树、打开的描述符生命周期），但诊断结果不能反过来证明旧锁安全。任何“新锁已加入，所以 #264 不再影响成长恢复”的说法都是错的。

## 3. 锁在已批准 D 流程中的位置（AC-3）

D 流程 = 完整备份 → 候选构建 → 逐文件发布 → 日志/完整性 → 完成/恢复，已在[恢复选项](ADVANCEMENT-RECOVERY-OPTIONS.md) §3 与[身份契约](ADVANCEMENT-IDENTITY-CONTRACT.md) §3.5 获批。“持锁”指持有 `SAVE`；内层锁按需再取。

| 阶段 | 何时持锁 | 该阶段动作（设计） | 失败时停止方式 | 可重试边界 |
|---|---|---|---|---|
| `admit` 受理 | **全程持锁** | 规范化存档路径；能力探测；存疑门；生成随机 `operation_id`；写 `stage=admit` | 探测/存疑门失败 → 不写任何目标文件，报告原因与所需人工动作 | 可重试：整次操作重新开始（新 `operation_id`） |
| `backup` 完整备份 | **全程持锁** | 在存档外独占创建备份目录；复制全部用户数据（排除集合须所有者确认）；逐文件记录路径/类型/大小/摘要；校验副本；同步文件与目录；写 `stage=backup_verified` | 空间不足、特殊文件、权限、同步失败 → 停止；保留不完整备份供人检查；不开始写目标 | 可重试：在同一操作内用新目录重做备份（旧的不完整目录保留） |
| `candidate` 候选构建 | **全程持锁** | 在同一文件系统/卷上建暂存树（跨设备直接拒绝）；按已验证前像生成候选；校验 schema/身份/关系与每文件目标摘要；写候选清单 | 空间不足、校验失败、候选期间检测到外部变化 → 停止；保留备份与不完整候选，记录位置 | 可重试：重建候选；**不得**把不完整候选标记为已验证 |
| `publish` 逐文件发布 | **全程持锁** | 固定顺序（默认：`sheets/*.yaml` → `combat/party-state.yaml` → `Characters/*.md` → `progress.yaml` → 追加日志 → 完整性清单）；每文件：写 intent → 复核当前内容=前像 → 同目录临时文件+rename → 同步文件与父目录 → 写 done | 任一复核不符/写失败/同步失败 → **立即停止**，不再发布后续文件；记录已发布/未发布清单；保留备份、候选与阶段记录 | 不自动重试发布。恢复时按“当前=目标→算已应用；当前=前像→可应用；都不是→停止”逐文件判断 |
| `logs` 日志与完整性 | **全程持锁**（完整性清单另取内层锁） | 追加日志按操作 ID 去重，不截断、不改写既有行；尾部异常时停止而不是“补齐”；完整性清单更新保留既有 dirty 标记，只登记本次确认写入 | 追加失败/清单失败 → 停止并报告“日志可能已追加、清单可能未更新”，不自动回滚 | 日志：仅在能证明未追加时可重试；清单：可重复重算但不洗掉 dirty |
| `complete` 完成 | **全程持锁** | 重新发现并比对候选清单：无意外新增/删除/变化才写 `stage=complete`；释放锁 | 比对不符 → 状态置 `in_doubt`，停止普通写入，要求人工 | 校验可重复；清理暂存/备份**不属于**成功证明，另按保留策略批准后执行 |
| `recovery` 显式恢复 | **全程持锁**（自身一个 `operation_id`） | 先保护恢复时的当前树（新备份）；校验原备份完整性；确认目标身份；逐文件比较当前内容与前像/目标；由人显式选择“回滚到前像”或“继续完成到目标”（各自独立记录）；逐文件执行并同步；再次中断走同一门 | 当前内容既非前像也非目标、日志已有后续追加、身份不明、备份校验失败 → 停止，保留两份证据，要求人工合并；不删除后续日志 | 恢复本身不自动重试；重复恢复以新 `operation_id` 重新判定，靠内容比较保证不重复应用 |

阶段报告的固定字段（用于人读和证据）：操作 ID、阶段、锁状态、备份位置、候选位置、已发布文件清单、未发布文件清单、结论（未写/部分写/已写）、需要的人工动作、不得自动执行的动作。

**明确不承诺**：不承诺多文件原子性；不承诺崩溃后自动恢复到一致状态；不承诺恢复会保留未在备份中的后续内容（只能由人选择）；不承诺锁能阻止非协作写者；不承诺目录同步/掉电语义（`fsutil::sync_parent` 在 Unix 忽略目录打开与同步错误、非 Unix 不执行）。**事实**：`fsutil::atomic_write` 成功返回不证明目录项已持久化。

**幂等与去重**：属性值、XP、资源、专长选择等“只加一次”的效果，必须由操作记录 + 每目标标记保证恰好一次，不能靠“数值看起来已经是新值”推断；日志去重只能用操作 ID 标记，不靠扫描猜测。校验、摘要、复制到新目录可重试；发布、日志追加、恢复动作在不能证明状态前不可重试。

## 4. 合成测试矩阵（AC-4）

全部 **NOT_RUN**。下表描述未来在**合成 fixture**（临时存档目录，无真实数据）上执行的测试；“CI”指三平台 GitHub Actions 可跑，“人工/特权”指需要多主机、网络文件系统、特权或物理操作。断言列是该场景下可判定的期望，不是当前结果。

| ID | 场景与注入 | Linux 期望 | Windows 期望 | macOS 期望 | 环境 | 判定要点 |
|---|---|---|---|---|---|---|
| T1 | 两个协作写者同时提交 | 一方取得锁，另一方在 deadline 后失败，失败方未写任何目标文件 | 同左（`LockFileEx`） | 同左（`flock`） | CI | 失败方输出含持有者记录；目标字节不变 |
| T2 | 持锁期间锁文件被外部删除/替换 | 下一阶段边界检测到文件标识变化，立即中止；第三方可能另持不同 inode 的锁，报告为已知限制 | 行为待实测：标准库的共享模式可能允许删除/重命名，**不能**假设 OS 会拒绝；无论 OS 拒绝还是成功，都必须中止并记录实际观察值 | 同 Linux | CI（替换由测试子进程执行） | 不得继续发布；不得宣称阻止了替换 |
| T3 | 活持有者超时（持有者仍在运行，等待方 deadline 到期） | 等待方失败，**不**删锁、**不**接管；持有者继续完成 | 同左 | 同左 | CI | 不得出现“第二个写者进入” |
| T4 | 崩溃/被杀（每个阶段边界 `SIGKILL` / `TerminateProcess`） | OS 释放锁；下次获取成功但存疑门拦下普通写入；备份与阶段记录可定位 | 同左（杀进程方式不同） | 同左 | CI | 不把未结束操作当成功；不自动继续发布 |
| T5 | 陈旧锁（记录很旧、无持有者） | 获取直接成功（OS 锁空闲），旧记录被报告并覆盖，不“抢占” | 同左；锁文件未被删除，仍可打开 | 同左 | CI | 释放后路径仍存在 |
| T6 | 顺序反转（checkpoint 快照/恢复 vs 成长提交） | 两者按总序串行，一方等待或失败，**不死锁**；等待方有超时判定 | 同左 | 同左 | CI（两进程 + 测试级超时） | 任一测试挂起即失败 |
| T7 | 非协作编辑（preview 后、发布前、复核后 rename 前各注入外部写） | 复核后 rename 前的写可能被覆盖：报告“无法排除覆盖”，记录前像/目标/实际三值；其前两处必须检出并拒绝 | 同左 | 同左 | 需实现后故障注入（测试夹具 + 注入点） | 明确 TOCTOU 未消除，不得标为“已修复” |
| T8 | 预览过期（绑定摘要/授权/遭遇状态变化） | 提交拒绝，要求重新预览，目标不变 | 同左 | 同左 | CI | 拒绝理由指向具体变化项 |
| T9 | 恢复中断（每个恢复阶段被杀后重启） | 重新进入存疑门，要求人选择；不重复应用、不删除后续日志、不覆盖保护备份 | 同左 | 同左 | CI（三平台各自跑） | 第二次恢复的判定基于内容而非阶段标签 |
| T10 | 释放语义（持有期间锁文件被替换后释放） | 释放不删除替换后的文件；路径仍存在；内容属于替换者 | 同左，但 Windows 可能的删除失败要单独断言 | 同左 | CI | 直接对应“不拆掉被持有的 inode” |
| T11 | 能力探测失败（只读目录、探针无法创建/删除、目录为网络挂载） | 失败关闭，拒绝提交；错误说明平台/文件系统 | 同左 | 同左 | 人工/特权（网络挂载、只读卷） | 不得降级为 `create_new` 或只读提交 |
| T12 | 跨主机/网络文件系统互斥 | **UNKNOWN**：本地探针通过不代表跨客户端互斥 | **UNKNOWN**（SMB/OneDrive） | **UNKNOWN**（NFS/云同步） | 人工/特权（第二台主机或挂载） | 未证明前按“不支持”处理 |

**只能由实现后的故障注入证明的结论**：T2/T7/T9 的阶段边界中止、发布前复核、日志去重、恢复不重复应用；T4 的“崩溃后不把不完整候选当已验证”；T10 的 inode 身份保护；以及任何“失败后目标字节未变/部分已变”的精确断言。**T11/T12 即使实现了也需要人工/特权环境**，不能进 CI 的常规绿灯。

**不进入 CI 的**：掉电/设备谎报同步、磁盘控制器缓存、文件系统修复、杀毒软件拦截、容器/虚拟机快照恢复、真实玩家存档与非协作文本编辑器。全部保持 UNKNOWN，需所有者决定是否另行验证。
