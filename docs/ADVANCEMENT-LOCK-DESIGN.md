# 成长协作锁域与恢复协议（设计）

状态：**仅设计**。本文不实现锁、不改代码、不迁移存档、不写 sidecar、不改变已批准的 B/D/Q 或备份/恢复边界。代码事实基线 `cc7876077d705598eed7f08ad7b365168efccfdc`；合成测试与故障注入**全部未执行**。依据 [身份契约](ADVANCEMENT-IDENTITY-CONTRACT.md) §3–§6、[恢复选项](ADVANCEMENT-RECOVERY-OPTIONS.md)、[安全审计](ADVANCEMENT-SAFETY-AUDIT.md)、[锁调查](CHECKPOINT-LOCK-INVESTIGATION.md) 与[成长设计](superpowers/specs/2026-11-10-character-advancement-design.md)。只读公开源码、测试与既有文档；未读取真实存档、书籍、DM 秘密。

标记约定：**事实**指能从当前公开代码/测试直接读出的行为；**推断**指由静态事实推出、未实测的后果；**UNKNOWN** 指本次不能判定，不等于安全。现有测试通过**不是**锁安全证据；#264 未解决前，任何“现有锁已够用”的结论都不成立。

## 0. 本文件回答什么、不回答什么

回答：新版本成长提交会碰哪些写入对象；它们今天受哪把锁保护、按什么顺序写；协作锁应当怎样定义身份、作用域、获取顺序、持有与失效；它嵌进已批准的 D 流程后各阶段何时持锁、失败怎么停、哪些动作可重试；Linux/Windows/macOS 上哪些结论能用合成测试判定。

不回答/不承诺：不承诺多文件原子性、不承诺消除 TOCTOU、不承诺约束旧二进制/外部编辑器/不遵守协议的进程、不承诺跨网络文件系统语义、不宣布 #264 已解决、不给实现排期、不改变任何既有安全承诺；预览不写存档，提交不承诺有界总等待（原因见 §2.4）。

### 1.2 现有两把锁的机制（逐条事实）

**checkpoint 锁 `.talkdnd.lock`**（`tools/talkdnd/src/checkpoint.rs`）：

1. 获取 = `OpenOptions::create_new(true)` 创建文件，写入本进程 PID（`Lock::acquire`）。**事实**：不持有任何 OS 文件锁。
2. 冲突 = 文件已存在；若 `stale()` 判定（mtime 距今 ≥ `LOCK_STALE_SECS = 600` 秒）则 `remove_file` 后重试一次（`stolen` 只允许抢一次），否则报“另一个 checkpoint 操作正在进行”。
3. 释放 = `Drop` 里 `remove_file(&self.path)`。**事实**：无归属校验、无 inode 校验。
4. 推论（**推断**，未实测）：(a) 进程被 `SIGKILL` 后锁文件留在原处，最长 600 秒内所有 checkpoint 操作被拒，之后任意后来者删除并接管；(b) 若 A 的快照超过 600 秒（大存档复制），B 会删掉 A 的锁并开工，两个写者同时操作同一存档；(c) 若 B 已接管并新建锁文件，A 结束时 `Drop` 会删除 **B 的** 锁文件，第三个写者因此可以进入；(d) `stale` 只看 mtime，不看持有者是否存活，也不看进程 PID——PID 只被写入、从未被读取。**这不是安全基底。**

**完整性锁 `.talkdnd.integrity.lock`**（`tools/combat-sim/src/integrity.rs`）：

1. 获取 = `OpenOptions::create(true).truncate(false).write(true)` 打开固定路径，再 `File::lock()`（Rust 标准库文件锁；Unix 为 `flock`，Windows 为 `LockFileEx`）。**事实**：阻塞等待，无超时；同一进程再次获取会自锁死（源码注释明确要求用 `*_locked` 变体）。
2. 释放 = 句柄 `Drop` 或进程退出，由 OS 释放。**事实**：崩溃不会留下“陈旧锁”；锁文件永不删除、从不参与完整性指纹。
3. 覆盖范围 = 只有 `integrity.yaml` 的读改写。**事实**：`audit::after_command`、`integrity::ensure/changes/after_write`、`migrate::carry_dirty_flags_guarded`、`checkpoint::restore_rebaseline` 在同一把锁下更新清单。

**顺序事实**：`checkpoint.rs` 模块注释声明 checkpoint 锁先、完整性锁后，“never the reverse”；`restore_inner` 全程持 checkpoint 锁，并在其中调用 `migrate::ensure`（内部会取完整性锁）与 `restore_rebaseline`。**事实**：这是当前代码里唯一成文的锁序。除此之外没有全序表，也没有进程内的“已持有集合”检查。

**普通命令的写序列（无保存级锁）**：`lib.rs::run` = 解析 →（多数命令）`integrity::snapshot`（无锁）→ `dispatch`（真正写入：`charsheet::commit`、`Progress::store`、`save::append` …）→ `audit::after_command`（此时才取完整性锁）。**事实**：写与清单更新之间没有互斥；`snapshot`/`dispatch`/`audit` 三段之间，另一个进程可以完整插入。

### 1.3 现有锁文件在备份/回滚中的位置（事实与风险）

- `checkpoint::copy_tree` 只跳过 `.talkdnd.lock`；`integrity::LOCK`（`.talkdnd.integrity.lock`）会被复制进备份/回滚镜像。
- `checkpoint::remove_extras` 同时跳过 `.talkdnd.lock` 与 `integrity::LOCK`（不回删）。
- 镜像回滚用 `copy_tree(&backup, save)` 写回；`std::fs::copy` 对已存在的目标是**截断写同一 inode**，不是替换 inode，但会**改写**该锁文件的字节内容。**推断**：若回滚发生时另一个进程正持有该 inode 的排他锁，OS 锁仍然有效，但基于文件内容的持有者记录会被污染；因此任何协议都应在取得 OS 锁之后才读记录，并且**不以锁记录作为“有无未结束操作”的唯一依据**（见 §2.2 的持久操作记录）。
- `migrate::copy_tree` 不跳过任何锁文件，备份里会出现这些锁文件的副本。**推断**：用它恢复/复制时可能把锁文件带到新位置，`(路径, inode)` 级别的锁身份不能因此被当成同一把锁。

### 1.4 现有测试能证明什么（不能证明锁安全）

| 测试入口（事实） | 实际覆盖 | 为什么不是锁安全证据 |
|---|---|---|
| `tools/talkdnd/tests/checkpoint.rs::a_held_lock_fails_the_second_call_and_a_retry_after_release_works` | 手工写入锁文件后，同一进程的快照/恢复被拒；删除后恢复 | 只验证“文件存在即拒绝”，不验证真实竞争、进程死亡或锁文件被替换 |
| `tools/talkdnd/tests/checkpoint.rs::concurrent_snapshots_exactly_one_wins` | **同进程两个线程**竞争一次快照 | 没有第二个进程；不覆盖 OS 锁、`Drop` 删除他人锁、stale 抢占 |
| `tools/talkdnd/tests/checkpoint.rs::restore_rebaseline_keeps_a_concurrent_writers_fingerprints`、`rollback_keeps_the_integrity_lock_a_concurrent_writer_holds` | 恢复/回滚期间清单锁与另一个“写者”的指纹 | 写者是测试自己构造的句柄/子进程，且 `rollback...` 正是 #264 首次失败点；#264 未解决 |
| `tools/combat-sim/src/integrity.rs` 测试（如清单锁失败不泄漏锁） | 清单读改写的互斥与错误路径 | 只覆盖清单这一把锁，不覆盖角色/party/进度/日志 |

**结论（事实）**：现有测试证明的是若干局部不变量，不是“成长提交在并发下安全”。#264 的首次 `WouldBlock` 根因仍 UNKNOWN，[锁调查](CHECKPOINT-LOCK-INVESTIGATION.md) 的后续通过不推翻这一点。

## 2. 协作锁协议（AC-2）

### 2.1 目标与不变式

协作锁只负责一件事：**让所有遵守本协议的新版本写者在同一个存档上串行执行“可能改变存档内容”的操作，并让崩溃/接管有可判定的状态**。它不是认证、不是防篡改、不约束不遵守协议的进程。锁文件只是互斥载体，**“是否存在未结束操作”由持久操作记录判定**（§2.2）。

| ID | 不变式 |
|---|---|
| I1 | 一个存档同一时刻最多一个遵守协议的持有者处于“可写阶段”。 |
| I2 | 锁文件一旦存在就**永不删除、永不 rename 覆盖**；只在同一 inode 上原地改写记录。 |
| I3 | 锁文件路径指向的 inode 在持有期间不得改变；检测到改变即中止，不继续写。 |
| I4 | 持有者存活由 **OS 锁**判定；记录里的时间/心跳/pid **不能**作为抢占依据。 |
| I5 | 获取失败一律失败关闭：不降级、不失锁重试为“只读提交”、不吞掉只报警。 |
| I6 | 锁只覆盖一个存档；跨存档不做全局互斥（不同存档可并行）。 |
| I7 | 锁不改变任何既有写入语义；既有内层锁（完整性、checkpoint）原样保留并仍按自己的规则工作。 |
| I8 | 任何阶段的失败都必须留下可定位的（操作 ID、阶段、备份位置、已写/未写）记录，且不得删除唯一可恢复副本。 |
| I9 | **判定未结束操作之前，不得截断、覆盖或“初始化”锁记录与持久操作记录**；预览不写存档（§2.7）。 |
| I10 | 无法证明“没有未结束操作”时一律失败关闭；新锁文件、空记录或记录缺失都不能当作干净。 |

### 2.2 锁身份、持久操作记录与位置

- **锁路径**：`Saves/<slot>/.talkdnd.advancement.lock`（存档根目录，与 `.talkdnd.integrity.lock` 同级）。
- **持久操作记录（P，权威）**：`Saves/_backups/.operations/<slot>/current.yaml`，位于存档之外（存档恢复不会移动或删除它），原子替换更新；终态副本归档到同目录 `history/<operation_id>.yaml`（每次 `create_new` 只写一次，不改写）。
  - P 字段（设计）：`schema`、`protocol_version`、`save_path`、`save_id`、`operation_id`、`mode`（`advance-commit` / `recovery` / `checkpoint` / `migrate`）、`stage`、`state`（`held` / `released` / `complete` / `failed` / `in_doubt`）、`created_at`、`updated_at`、`backup_dir`、`candidate_dir`、`lock_file_identity_at_acquire`、`published[]`（路径 + 前像摘要 + 目标摘要 + 完成标记）、`not_published[]`、`last_error`、`recovery_of`（恢复类操作）。
  - P 是控制元数据，**不是**用户数据；不写日志正文、角色内容或秘密。P 的写入用 `temp + rename`（rename 目标只在 `.operations/` 内，**不得**触碰锁路径）。
- **作用域**：该存档目录下的全部内容文件，加上本次操作的备份目录与候选目录（由 P 引用）。
- **锁身份**（三层）：
  1. **存档身份**：`canonicalize` 后的存档真实路径（拒绝非目录、拒绝解析后逃出 `Saves/` 的路径）。
  2. **锁文件身份**：打开句柄的文件标识（Unix：`dev`+`ino`；Windows：文件索引/文件 ID，或等价可复核标识）。它只在持有期间自检“我锁的路径有没有被换”，**不能**用来发现旧 inode 的其他持有者（§2.5）。
  3. **持有令牌**：每次获取生成随机 `owner_id`；同一进程内后续调用以“已持有句柄”传递，不重新获取。
- **锁记录内容**（诊断，不是权威）：`schema`、`owner_id`、`pid`、`host_label`（默认空）、`tool`+`version`、`operation_id`、`state`、`acquired_at`、`heartbeat_at`、`notes`。
- **不变量**：先拿到 OS 锁，再**只读**读取；判定完成后才允许写。任何基于记录内容（时间、pid、state）的抢占都不允许。

### 2.3 获取、检视、释放与重入

获取（提交/恢复/受管 checkpoint/migrate 的入口）：

1. 解析并规范化存档路径；不满足则拒绝，**不创建**任何文件。
2. 打开前先 `lstat` 记录锁路径是否存在（这是 §2.6 判定的输入之一）。若 `lstat` 不存在但 P 已存在或 `history/` 非空 → **直接失败关闭，不创建文件**。常规获取用 `create(true).truncate(false).read(true).write(true)` 打开已存在的锁文件；只有 §2.5 的“首次初始化”分支允许一次 `create_new`。
3. 用 `try_lock` 在**有界 deadline** 内轮询（默认 5 秒，可由显式参数覆盖；见 §2.4 与 §5 ED-3）。到期即读取记录（只读）并失败，错误带脱敏持有者信息与人工动作。
4. 取得 OS 锁后复核“路径 → 同一文件标识”；若已被删除/替换：释放、重新打开（有限次数），仍不一致则失败并报告“锁文件被替换”。
5. **只读阶段**：读取锁文件字节（区分“不存在”“0 字节”“不可解析”）与 P（`current.yaml`、`history/` 列表）。**此时不截断、不写入、不删除任何记录。**
6. 按 §2.6 判定。只有判定为“干净”“上次失败在发布前”或“首次初始化”时才继续；未结束/未知一律拒绝（释放 OS 锁，不写任何目标文件）。
7. **持久化新关联**（仅在允许后；先在本进程生成随机 `operation_id`）：
   1. 原子替换 `current.yaml` 为新操作记录（`state=held, stage=admit, published=[]`）；
   2. 失败则**不**写锁记录、释放、报告；
   3. 成功后**原地**写锁记录（截断 + 写 + `sync_all`），再从同一句柄读回比对 `owner_id`；
   4. 锁记录写/同步失败 → 原子替换 `current.yaml` 为 `state=failed, stage=admit, published=[]`，报告并释放，不写目标文件。
8. 通过后才进入阶段机（§3）。

释放：

1. 原子替换 P 为终态（`released` / `complete` / `failed` + 最后阶段 + 已发布清单），`sync_all`；
2. 归档 `history/<operation_id>.yaml`（`create_new`；已存在则不覆盖，报告）；
3. 释放 OS 锁；
4. **永不** `remove_file` 锁文件；若路径已被替换，仅记录并释放，不改动替换后的文件。

记录写入失败、短写、崩溃时如何保留旧关联：

- 分类前只读，所以**旧 P 与旧锁记录在判定前不会被破坏**；崩溃只可能留下“旧记录”或“新记录”（P 用原子替换）。
- P 替换失败/短写/同步失败 → 旧 P 仍在；临时文件残留不改变 `current.yaml`；操作停止，不写锁记录，不写目标文件。
- 锁记录短写/同步失败 → P 已是新操作但状态改为 `failed/published=[]`；下一次获取看到“未结束但未发布”，可以重试，不会误判为完成。
- 崩溃发生在“P 未更新、但目标文件已开始发布”的情形被设计排除：**每文件发布前必须先持久化该文件的 intent 到 P**；intent 写失败则不得发布该文件。若实际观察到“目标已变而 P 无对应 intent”，按未知失败关闭。
- 崩溃发生在 `history` 归档前 → 只有 P；不影响判定（history 是审计副本）。
- 锁文件记录被撕成不可解析但 P 完整且 `state=held`、`lock_file_identity_at_acquire` 等于当前文件标识 → 容忍锁记录损坏并报告，P 仍权威；若标识不一致 → 按 §2.5 的“锁被替换”处理。

重入与顺序：

- **总序**：`SAVE（协作锁）` → `checkpoint .talkdnd.lock` → `integrity .talkdnd.integrity.lock`。反向获取算协议违规（进程内“已持有集合”直接报错，不依赖死锁超时）。
- 同一进程同一存档最多持有一个 `SAVE` 句柄；嵌套步骤接收该句柄（`*_locked` 风格），不重新打开。
- 子进程/子命令不继承锁，也不允许“父进程持锁、子进程写”；跨进程工作必须在释放后由子命令重新获取。
- 现有 checkpoint 路径（只取自己的锁）在接入前仍是“旧写者”；接入后 checkpoint 也必须先取 `SAVE`，否则总序不成立。

### 2.4 超时、租约、等待预算与内层锁

- **持有不是租约**：不用 TTL 判定持有者死亡，不因超时删锁、改名或“接管”。理由：checkpoint 锁的 600 秒抢占正是同类风险来源；活持有者超时被抢会产生两个写者。
- **获取有 deadline**：等待方在 deadline 后失败，不无限阻塞。
- **等待预算必须覆盖整条调用链**：一次操作的总等待 = `D_save`（SAVE 获取）+ 各阶段内层锁获取的 `D_inner` 之和。实现必须为**每一次**内层获取指定 deadline 与取消路径，并在超预算时失败；`D_save` 单独满足**不能**当作整体有界保证。
- **内层锁现状（事实）**：完整性锁 `File::lock()` 是阻塞调用、无超时；checkpoint 锁是 `create_new`，不等待但不提供存活语义。**因此当前任何在 SAVE 内获取完整性锁的路径（`audit::after_command`、`PartyState::save`、`migrate::ensure`、`integrity::*` 等）都无法给出有界总等待。**
- **接入停止条件（强制）**：在内层锁获得有界获取/取消能力之前，含完整性锁的提交路径**不得接入**，也不得把 `D_save`、T1/T3 的（未来）结果外推为“整条提交路径有界”。可选做法：(a) 给完整性锁增加带 deadline/可取消的获取（行为变更，需审查）；(b) 把清单更新移出关键段并接受不同的失败语义（需所有者决定，见 OD-9）；(c) 保持无限阻塞并明确不承诺有界等待（则提交路径不得宣称有界）。本文不替所有者选。
- **心跳仅用于诊断**：阶段切换、长复制前后、每文件发布前后更新 `heartbeat_at`；心跳陈旧但 OS 锁可用时获取会正常成功（OS 已释放），旧记录进入 §2.6 判定，不需要“抢”。
- **人工强制**：只在操作者明确要求时提供 `--force-release` 一类动作，写清目标操作 ID、理由、证据位置；它只能清理**记录状态**或提示人工删除锁文件，不能解除另一个进程持有的 OS 锁，绝不宣称“已解锁”。

### 2.5 崩溃、锁文件被替换与平台原语

- **崩溃/被杀**：OS 释放锁；P 留在 `held` 或 `in_doubt`。下一次获取成功，但 §2.6 会拦下普通写入，要求显式恢复。
- **锁文件被删除/替换（A 持旧 inode、B 新建文件）**：
  - **权威是 P，不是锁文件**。锁文件为空、不存在或新建，**都不能**说明没有未结束操作。
  - B 取得新文件上的锁后仍须读 P：若 P 显示未结束操作 → B **拒绝普通写入**，并报告“旧持有者可能仍在运行，且无法证明其不存在”。
  - 路径→句柄复核只能发现“B 自己锁的路径被换”，**不能**发现 A 仍持有旧 inode 的 OS 锁；不得声称该复核足以发现旧持有者。
  - 若 P 记录 `lock_file_identity_at_acquire` 与 B 看到的当前标识不同 → 记录“锁文件在未结束操作期间被替换”的证据（两个标识、时间、操作 ID），进入存疑/人工隔离。
  - A 若在路径被替换后继续写，属于“协议外行为”：A 在下一阶段边界自检会发现自己的路径标识变化并中止，但若替换发生在 A 的最后一次自检之后，A 的写入仍可能落地——这是无法消除的窗口，只能报告。
  - 缺失/新建锁文件的**可信条件**：
    1. 唯一可信的“新建”是**首次初始化**：打开前 `lstat` 不存在，且本次用 `create_new`（O_EXCL）成功创建；随后取得 OS 锁、确认 P 与 `history/` 都不存在，才允许开始第一个操作。`create_new` 返回 `AlreadyExists`（哪怕文件是 0 字节或刚被别人创建）→ 进入“存在但 P 缺失”分支，**失败关闭**。
    2. 正常（非首次）获取永远用 `create(true)` 打开已有文件，绝不创建新文件、绝不删除旧文件。
    3. 任何“锁文件存在”的情形都不能单独证明干净；是否干净只由 §2.6 用 P 与 `history/` 判定。A/B 反例见 T2c（全部 NOT_RUN）。
- **平台原语**（**事实**：现有代码已用 `std::fs::File::lock` / `try_lock`）：
  - Linux：`flock`，advisory，按打开文件描述；同进程二次打开会自阻。本地 ext4/xfs/btrfs 需实测；NFS/FUSE/网络盘 **UNKNOWN**。
  - macOS：`flock`，advisory；APFS 本地盘需实测；网络卷/云同步目录 **UNKNOWN**。
  - Windows：`LockFileEx`（字节区锁，强制性更强）；**推断（未在本项目实测）**：标准库默认共享读写与删除，另一个进程可能仍能删除/重命名锁路径，因此不能依赖 OS 拒绝；共享模式、杀毒软件、OneDrive、网络盘 **UNKNOWN**。
  - **能力探测**（只在提交/恢复时、取得锁之后执行）：在存档目录创建一次性探针 `.talkdnd.probe.<random>`，取锁后用第二个句柄确认被拒，再释放并删除；失败、无法删除、目录不可写 → 失败关闭并报告残留路径。同一进程探针只证明 API 可用，**不证明跨主机互斥**。
  - **不支持时的策略**：不降级（不退回 `create_new`、不退回“只读提交”、不静默继续）；只允许预览/只读诊断。是否允许所有者显式绕过见 §5 OD-1/OD-6。

### 2.6 存疑门（in-doubt gate）

判定只用两样东西：锁文件字节状态（存在/0 字节/不可解析）与 P（`current.yaml` + `history/`）。**“无记录”不等于干净。**

| 锁文件（打开前 `lstat`） | P（`current.yaml`） | 判定 | 动作 |
|---|---|---|---|
| 不存在，且本轮 `create_new` 成功 | 不存在，`history/` 为空 | **首次初始化** | 允许创建第一个操作；只记录“此前无本协议记录”，**不**声称该存档从未被写过 |
| 存在（含 0 字节/不可解析），或 `create_new` 返回 `AlreadyExists` | 不存在 | 无法区分（旧版锁、记录丢失、非协作创建） | **失败关闭**，要求人工检查；不删除、不覆盖 |
| 任意 | 不存在，但 `history/` 非空 | 记录缺失 | **失败关闭** |
| 任意 | 存在但不可解析/短写 | 未知 | **失败关闭** |
| 存在 | `state ∈ {released, complete}` 且 `published[]` 与记录一致 | 干净 | 允许新操作，先报告上一操作 ID 与备份位置 |
| 存在 | `state=failed`、`published[]` 为空、`stage ∈ {admit, backup, candidate}` | 上次失败在发布前 | 允许新操作（报告上一操作 ID 与备份），并保留旧备份 |
| 存在 | `state=failed` 且 `published[]` 非空 | 未结束（部分发布） | **拒绝普通写入**，只允许检查/恢复 |
| 存在 | `state ∈ {held, in_doubt}` | 未结束 | **拒绝普通写入**，列出操作 ID、阶段、备份、已写/未写结论 |
| 任意 | `state=held` 且 `lock_file_identity_at_acquire` ≠ 当前文件标识 | 锁被替换 | **拒绝**并报告两个标识；不得声称旧持有者不存在 |

只有“干净”“上次失败在发布前”“首次初始化”三类允许创建新持有记录；其余必须先由显式恢复或人工隔离解除。

### 2.7 预览必须只读

已批准边界是“预览不写”。因此预览：

- **不获取 `SAVE`、不打开/创建锁文件、不写探针、不写 `.cache`、不更新 P**；只做只读发现与读取。若实现需要缓存，只能写到调用方显式指定的**存档外**路径，并标注“非证据、可能过期”。
- **绑定**：`preview_id` = 对（完整枚举清单 + 每文件摘要 + 规则集 + 授权状态 + 遭遇状态 + 身份映射 + 计划变更）的摘要；由调用方保存（stdout 或显式 `--out` 存档外路径）。预览**不**持久化绑定。
- **不跨预览→提交持有**：预览与提交之间不持有任何锁、也不发长期租约；提交时的重新发现与 `preview_id` 比对是唯一一致性依据。持锁等待玩家决策会产生无限期占用且无法安全回收，因此不采用。
- **一致性声明**：预览输出必须写 `consistency: unverified`，说明读取期间可能有并发写者、结果不是快照。
- **提交复核**：提交必须取得锁、重新发现并重算 binding，与传入的 `preview_id` 比较；不一致就拒绝并列出差异类别，要求重新预览；未提供 `preview_id` 时拒绝（与“提交重新验证”一致）。
- **锁缺失/只读目录/能力未探测时**：预览照常可跑（它不需要锁），但必须报告 `write_capability: unverified`，不得承诺可提交；是否可提交只在提交时由能力探测与 §2.6 判定。
- **不自行改变决定**：若未来要求预览把 binding 写进存档（例如 `.cache/preview.yaml`），那是改变“预览不写”的已批准决定，**须所有者重新授权**；本文不这样做。

### 2.8 与现有锁共存、以及锁域之外的写者

- **共存**：`SAVE` 是最外层；checkpoint 锁与完整性锁保持原语义（§1.2）。`SAVE` 不取代它们，也不改变 `integrity` 的承诺；迁移/恢复把两把旧锁当内层锁，取 `SAVE` 之后才取。
- **必须先修掉的旧行为**（后续实现任务，不是本任务）：checkpoint `Drop` 无条件删除锁文件；`stale()` 按 mtime 抢占；备份/回滚复制锁文件；`migrate::backup_save` 静默跳过特殊文件。这些与 I2/I3/I4 冲突；**在修掉之前，新锁只约束遵守新协议的写者**。
- **不受约束的写者**：旧版本二进制、外部编辑器、脚本、同步客户端、杀毒软件、备份工具、其它机器客户端（网络盘）、PDF 转换进程、手工复制。
- **当前 `combat-sim` 也不在锁域内**：它写遭遇/party 时不取 `SAVE`。接入前，提交必须把“可能的遭遇写入”当并发风险处理（活动遭遇只预览、检出变化即停）。
- **残余 TOCTOU（无法消除）**：每文件 rename 前复核仍有窗口；只能缩小窗口、记录复核值、失败时说明“可能已覆盖某次外部写入”。**#264 未解决期间同样适用。**
- **#264**：本设计不解释也不修复首次 `WouldBlock`。实现必须提供诊断模式（锁 inode、进程树、描述符生命周期），但诊断不能反证旧锁安全；任何“新锁已加入所以 #264 不影响成长恢复”的说法都是错的。

## 3. 锁在已批准 D 流程中的位置（AC-3）

D 流程 = 完整备份 → 候选构建 → 逐文件发布 → 日志/完整性 → 完成/恢复，已在[恢复选项](ADVANCEMENT-RECOVERY-OPTIONS.md) §3 与[身份契约](ADVANCEMENT-IDENTITY-CONTRACT.md) §3.5 获批。“持锁”指持有 `SAVE`；内层锁按需再取。预览不属于本流程（§2.7）。

| 阶段 | 何时持锁 | 该阶段动作（设计） | 失败时停止方式 | 可重试边界 |
|---|---|---|---|---|
| `admit` 受理 | **全程持锁** | 规范化路径；§2.6 **只读**判定（先证明干净/可重试；首次初始化按 §2.5 的 `create_new` 分支）；能力探测；生成 `operation_id`；原子替换 P 为 `state=held, stage=admit`；写锁记录并读回 | 判定为未结束/未知、探测失败、P 写失败 → 不写任何目标文件；报告操作 ID/阶段/残留探针 | 可重试：整次操作重新开始（新 `operation_id`）；首次初始化只在判定允许时发生 |
| `backup` 完整备份 | **全程持锁** | 在存档外独占创建备份目录；复制全部用户数据（含既有用户备份；控制元数据排除见 OD-7）；逐文件记录路径/类型/大小/摘要；校验副本；同步文件与目录；P 写 `stage=backup_verified` | 空间不足、特殊文件、权限、同步失败 → 停止；保留不完整备份供人检查；不写目标 | 可重试：同操作内用新目录重做备份（旧的不完整目录保留） |
| `candidate` 候选构建 | **全程持锁** | 在同一文件系统/卷建暂存树（跨设备拒绝）；按已验证前像生成候选；校验 schema/身份/关系与每文件目标摘要；P 记候选清单 | 空间不足、校验失败、候选期间检测到外部变化 → 停止；保留备份与不完整候选 | 可重试：重建候选；**不得**把不完整候选标记为已验证 |
| `publish` 逐文件发布 | **全程持锁** | 固定顺序（默认 `sheets/*.yaml` → `combat/party-state.yaml` → `Characters/*.md` → `progress.yaml` → 追加日志 → 完整性清单）；每文件：P 写 intent → 复核当前=前像 → 同目录临时文件+rename → 同步文件与父目录 → P 写 done | intent 写失败 → 不发布该文件；任一复核不符/写失败/同步失败 → **立即停止**，不再发布后续文件；记录已发布/未发布清单 | 不自动重试发布；恢复按“当前=目标→已应用；当前=前像→可应用；都不是→停止”逐文件判断 |
| `logs` 日志与完整性 | **全程持锁**（完整性清单另取内层锁） | 追加日志按操作 ID 去重，不截断、不改写既有行；尾部异常时停止；清单更新保留既有 dirty 标记，只登记本次确认写入 | 追加失败/清单失败 → 停止并报告“日志可能已追加、清单可能未更新”，不自动回滚 | 日志：仅在能证明未追加时重试；清单：可重算但不洗掉 dirty |
| `complete` 完成 | **全程持锁** | 重新发现并比对候选清单：无意外新增/删除/变化才写 `stage=complete` 并归档 history；释放 | 比对不符 → P 置 `in_doubt`，停止普通写入，要求人工 | 校验可重复；清理暂存/备份**不属于**成功证明 |
| `recovery` 显式恢复 | **全程持锁**（自身一个 `operation_id`） | 先保护恢复时当前树（新备份）；校验原备份完整性；确认目标身份；逐文件比较当前内容与前像/目标；由人显式选择“回滚到前像”或“继续到目标”（各自独立记录）；逐文件执行并同步；再次中断走同一门 | 当前内容既非前像也非目标、日志已有后续追加、身份不明、备份校验失败 → 停止，保留两份证据，要求人工合并；不删除后续日志 | 不自动重试；重复恢复以新 `operation_id` 重新判定，靠内容比较避免重复应用 |

阶段报告的固定字段：操作 ID、阶段、锁状态、P 位置、备份位置、候选位置、已发布文件清单、未发布文件清单、结论（未写/部分写/已写）、需要的人工动作、不得自动执行的动作。

**明确不承诺**：不承诺多文件原子性；不承诺崩溃后自动恢复；不承诺恢复保留未在备份中的后续内容；不承诺锁能阻止非协作写者；不承诺目录同步/掉电语义（`fsutil::sync_parent` 在 Unix 忽略目录打开与同步错误、非 Unix 不执行）。**事实**：`fsutil::atomic_write` 成功返回不证明目录项已持久化。

**幂等与去重**：属性值、XP、资源、专长选择等“只加一次”的效果，必须由 P + 每目标标记保证恰好一次，不能靠“数值看起来已是新值”推断；日志去重只能用操作 ID 标记。校验、摘要、复制到新目录可重试；发布、日志追加、恢复动作在不能证明状态前不可重试。

| ID | 场景与注入 | Linux 期望 | Windows 期望 | macOS 期望 | 环境 | 判定要点 |
