# 自动游玩反馈试点

仓库所有者可在一台受控 DM 主机上开启自动游玩反馈。开局、续档、检查点快照和恢复、战斗反应的结果会留在游玩根目录的 `.talkdnd/playtest-feedback/`。玩家继续使用原有游玩命令。

## 启用和停止

- 默认关闭。主机所有者在 DM 的进程环境中将 `TALKDND_PLAYTEST_FEEDBACK` 设为 `1`，启用本地记录。
- 要开启后台发单，在该主机安装 GitHub CLI `gh`，将其所在绝对目录加入 `PATH`，并由主机的安全凭据配置提供 `TALKDND_PLAYTEST_GH_TOKEN`。使用仅能读写 `ctrlshiftaltdel/TalkDND` Issues 的独立凭据。没有专用凭据时，队列只保留在本地。
- 要停止新的记录和上报，从 DM 进程的环境移除 `TALKDND_PLAYTEST_FEEDBACK` 并重启该进程。若要立即阻止已启动的后台请求，撤销专用凭据。已经提交的 Issue 仍可在 GitHub 上处理。

## 记录和上报范围

最近两场按本机成功开局或续档划分。检查点恢复中确认回滚失败时立即入队。其他可识别的技术故障按同一操作阶段和事件码在两场内累计达到三次时入队。成功、等待玩家反应、正常拒绝和无法分类的结果仅计入本地。程序记录秒级耗时区间供本地试点观察。

发单在游戏命令释放锁后由独立后台流程执行。Issue 只使用预定义的阶段、事件码、程序版本、平台、规则版、计数档位和故障指纹。存档、路径、人物名称、命令参数、游玩文本、错误原文和令牌都留在本机。主机所有者可本地查看 `state.json` 中的汇总计数与关联 Issue 编号。

每个故障指纹使用同一张 Issue。断网后，后续游玩命令可以重试待处理队列。若创建请求结果不明，后续只查询对应 Issue，等待关联结果。这种情况下，自动发单不会重复创建。记录失败和断网不会改写游玩命令本身的输出、退出码或存档。
