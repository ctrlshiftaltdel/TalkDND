# AI 搜索性能与快速推演可行性探测（TASK-0095 / Issue #179）

状态：测量与设计探测，**不包含搜索实现**。本文回答 P7（Issue #176）开工前必须知道的一件事：在现有引擎上，动作级搜索、回合级推演和 Monte Carlo rollout 各能买到多少节点。

- 引擎基线：`4bb287889f0805cf43a5cdef2189855f351b0718`（`origin/main`，P5 合并后；本任务不改 `src/`）。
- 基准代码：`tools/combat-sim/tests/ai_search_perf.rs`（本 PR 新增，`#[ignore]`，只接受 release）。
- 参考运行的完整输出贴在 PR 证据评论；本文数字来自该输出。

## 1. 结论摘要

1. **动作规则结算本身很便宜。** 在 release + `NullSink` 下，单动作 P50 为 **2.9–15.9 µs**，P95 为 **3.2–26.3 µs**（多目标 AoE 最慢）。单回合（一个 AI actor 的完整 `take_turn`）P50 为 **4.0–16.6 µs**。
2. **`EncounterState` clone 也很便宜，前提是 log 已被清空。** 带自然小 log 的 `clone + clear` P50 为 **0.31–0.86 µs**；如果 clone 的 state 已经积累了 256 行 log，则 P50 升到 **12.2–12.5 µs**。搜索实现必须用 `NullSink` 并在 clone 后立即清 log，否则节点成本由日志而不是规则决定。
3. **预算内的节点量级很高。** 以“clone+clear + 一个动作”为一个节点，P50 口径下 100 ms 可容纳约 **6.0k–30.7k** 个节点（多目标 AoE 约 6.0k，其余 10^4 量级），300 ms 约 10^4，1000 ms 约 10^5。以“clone+clear + 一个 AI 回合”为节点，100 ms 仍有约 **5.7k–22.9k** 个节点。
4. **完整 4v4 rollout 约 0.20 ms/次。** 同一台机器单线程约 **2.3M rollouts/s**（该场景只有 8 个 combatant、中位 7 轮）。100/300/1000 ms 分别约 **500 / 1.5k / 5.0k** 次完整 rollout。
5. **P7 默认建议方案 A：仅在 `ai.rs` 内做浅层、有界、默认关闭的搜索。** 1 层动作/目标枚举，或 2 层 top-K 且只建模对手最佳回应；节点预算 256–512 个为主，100 ms 为软上限、300 ms 为硬上限；预算耗尽或遇到未支持效果时回退 UtilityPlanner/现有启发式。
6. **不建议把方案 B（`engine.rs` 快速 preview/transition）作为 P7 前置。** 现有动作已经是微秒级，B 的可压缩空间有限，却要改规则引擎并承担 preview 与真实结算不一致的风险。只有当真实内容上的节点成本显著高于本基准（见 §9 的触发条件）时，才另开任务实现 B。
7. **不建议在 P7 做 MCTS。** 小遭遇战里 rollout 确实便宜，但 100 ms 预算只有约 500 次 rollout，300 ms 约 1.5k 次；对 7 轮、8 个 combatant、分支较大的战斗不足以稳定估计动作价值。此外 P7 的范围明确是 1–2 层、默认关闭，不应在没有浅层基线的情况下承诺 MCTS 级质量。

### 2.2 指标定义

- **action**：从一个已 clone 好的 state 出发，调用一次引擎动作原语（`engine::attack_at` 或 `engine::use_ability`），计时**不含** clone。每次采样前 clone 在计时窗口之外完成。
- **turn**：从一个已 clone 好的 state 出发，调用一次 `Ai::take_turn`，计时不含 clone；`Ai` plan 在采样前只构建一次（与 `sim.rs` 的用法一致）。
- **clone+clear**：计时 `EncounterState::clone()` 后立即 `log.clear()`。分别测自然 log（初始化后的少量行）和人为填充 256 行 log 的敏感性。
- **rollout**：`sim::play_quiet(state.clone(), &ai, &mut rng, 50)` 跑完一场 4v4；计时包含 `play` 内部的 `engine::init` 与完整回合循环，不含外层 clone。
- **节点预算**：`budget_ms * 1000 / (p50_clone + p50_action 或 p50_turn)`，取 P50，不计入 AI 候选生成、对手建模和重复状态检测的额外开销。因此这是**乐观上界**。

## 4. 分析

### 4.1 时间花在哪里

- **规则结算不是毫秒级瓶颈。** 近战/远程/单目标法术的动作 P50 在 3–6.5 µs；只有多目标 AoE 达到约 16 µs。`DESIGN-v2.md` 里“每次攻击/施法的通用规则结算”是相对批量模拟的吞吐瓶颈，但绝对成本很小，不足以支撑“必须先在 engine.rs 做快速 preview”的结论。
- **AI 决策本身也不贵。** `Ai::take_turn` 只比对应动作多 1–4 µs（法术/多目标场景因为要在多个候选动作间评分，多约 1–2 µs）。AI plan 预计算后，每回合的评分开销没有数量级跳变。
- **clone 的形状很关键。** 自然 log 下 clone+clear 低于 1 µs；256 行 log 时变成 12–17 µs，约为动作成本的 2–5 倍。也就是说，**搜索节点最大的可控成本是日志，不是引擎**。任何搜索实现都必须：
  1. 用 `NullSink` 或等价 sink；
  2. 在 clone 后立刻 `log.clear()`；
  3. 不要把“已经积累了整场战斗 narrations”的 state 当作搜索 base。
- **多目标 AoE 是单动作里最贵的**（P50 15.9 µs，P95 26.3 µs），因为一个动作要遍历区域内所有目标、逐个豁免和结算伤害。它仍然允许 100 ms 内约 6k 个节点。
- **grid + 大体型 + multiattack** 的回合 P50 约 7.2 µs，动作 P50 约 3.1 µs；大致与 zone 场景同量级。体型/空间没有引入新的数量级。

### 4.2 节点量级的读法

- 100 ms 的动作级预算已经是 **10^4 量级**（多目标 AoE 为 10^3）。1 层枚举即使把候选动作×目标×移动航点做到 100–500 个节点，也只需约 1–10 ms。
- 2 层 top-K（K=8）在最坏情况下约 64 个动作节点；再加对手最佳回应（×8）约 512 个节点，按 16 µs/节点约 8 ms。仍在 100 ms 软上限内。
- 这些数字是**乐观上界**：候选生成、合法性过滤、状态去重、对手建模、真实内容的条件/触发器/反应都不在计时内。真实内容上建议按 2–5 倍安全系数估算；即便如此，100 ms 仍足以支持 1–2 层有界搜索。
- 回合级预算同样在 10^4（100 ms），因此“每个候选动作跑一整个 AI 回合”的朴素实现也不是不可行；但它会把对手/后续行动混进同一个节点，语义不如动作级清晰。

### 4.3 观察到的 API 缺口（不改源码，仅记录）

1. `Ai` 的 `CombatantPlan` / `PlannedAction` / 评分函数都是私有；外部无法枚举或复用 AI 的候选与评分。P7 在 `ai.rs` 内实现搜索可以直接复用，但 `sim.rs`/测试不能从外部驱动单动作 AI 决策。
2. `Ai::take_turn` 是唯一的公开决策入口，且一次跑完整回合，不能在中途暂停、分支或回滚。动作级搜索需要 P7 在 `ai.rs` 内新增一个“候选 → 克隆 state → 执行一个动作 → 评估”的路径。
3. 引擎的 `attack_at` / `use_ability` / `use_planned_ability` 是公开的，足以作为搜索的**执行与最终验证**原语；但它们按名字查找、消耗动作经济，并且会触发 reactions/triggers。搜索需要独立 RNG，且必须接受“search 的骰子不进入真实执行”的约束（P7 AC-1）。
4. 没有公开的“clone 但不复制 log”或“临时关闭 log 的 state 视图”。`clone + log.clear()` 是当前可行做法；成本已测。
5. 没有状态哈希/重复状态检测 API。P7 AC-3 若要做重复状态管理，需要在 `ai.rs` 侧自行定义轻量键（例如 combatant HP/条件/位置/回合的元组），不能依赖引擎提供。
6. 移动与动作不是原子 transition：AI 先 `move_for_action` 再执行动作。搜索若把“移动+动作”当一个节点，需要在 `ai.rs` 内组合，且要处理机会攻击/触发器的中间状态。这是方案 A 的主要实现风险之一。

## 5. 三种方案比较

| | A：仅 `ai.rs` 浅层搜索 | B：`engine.rs` 快速 preview/transition | C：近似模型 + 最终引擎验证 |
|---|---|---|---|
| 改动面 | `ai.rs`（P7 允许路径），可调用公开引擎原语 | `engine.rs`（本任务禁改；需另开任务） | `ai.rs` 的评估器 + 最终调用引擎原语 |
| 单节点成本（实测/推断） | clone 0.3–0.9 µs + action 3–16 µs | 理论上可低于 action 原语，但当前 action 已很小；收益上限有限 | 近似评分可到亚微秒级；最终验证仍需 3–16 µs |
| 100 ms 可买到的节点 | 10^3–10^4（动作级） | 取决于 preview 能省多少；天花板不高 | 10^5+（近似层），但最终验证次数受限于真实动作成本 |
| 规则一致性 | 高：搜索与执行走同一引擎原语 | 风险最高：preview 必须与真实结算保持一致 | 中：近似模型必然与引擎有偏差，需最终验证兜底 |
| 实现风险 | 中：候选生成、移动+动作组合、评分复用 | 高：改核心引擎、双路径维护、回归面大 | 中高：模型校准、边界效果、可能“优化了错误的目标” |
| 对 P7 的适配 | 直接适配（1–2 层、top-K、默认关闭） | 超出 P7 允许路径 | 可作为 2 层以上的备选，但不是默认 |
| 结论 | **推荐作为 P7 默认** | **不在本任务实现；仅在触发条件下另开任务** | **保留为深度搜索的后备，不作为 P7 默认** |

### 5.1 方案 A 的风险与边界

- 搜索必须复用 P6 UtilityPlanner 的候选/效用框架，否则会形成第二套评分逻辑。
- 移动候选必须 top-K/航点剪枝（P7 AC-9），不能枚举全部可达格；本基准没有测量移动枚举成本，P7 必须单独设上限。
- 搜索中的 reactions/triggers 会消耗 RNG 和一次性资源；必须在 clone 上执行，真实 state 不受影响（P7 AC-1）。
- 固定 seed 下排序可复现；若用 wall-clock 预算，排序会随机器负载变化。建议**节点预算为主、wall-clock 为安全阀**。
- 搜索失败/预算耗尽/遇到未支持效果时必须回退 UtilityPlanner 或现有启发式（P7 AC-5）。

### 5.2 方案 B 的触发条件

只有满足以下任一条件，才建议另开 `engine.rs` 任务评估 B：

1. 在真实内容（含条件、触发器、反应、更多 combatant）上测得单动作 P95 持续 > 100 µs，或单节点 > 50 µs；
2. P7 的 1–2 层搜索在 100 ms 内无法覆盖最小候选集（例如 < 32 个节点）；
3. 需要 3 层以上搜索或 MCTS，且近似模型（C）无法达到可接受的质量；
4. 日志/克隆成本通过 `NullSink` + 清 log 仍无法压到可接受范围（当前不是）。

B 的实现必须是独立任务，附带 preview 与真实结算的一致性测试；不得在 P7 中顺手改 `engine.rs`。

### 5.3 方案 C 的定位

- 近似模型（期望伤害/命中率/资源机会成本）可以把单节点压到亚微秒级，适合 3 层以上或大规模候选。
- 但它无法可靠覆盖条件互动、reactions、区域触发、空间阻挡等；必须保留“最终候选用真实引擎验证”的步骤。
- 在本基准的动作成本下，C 的收益不足以抵消模型偏差风险；建议只在 P7 的浅层基线证明“深度不够”后再开。

## 6. 关于 MCTS 的证据

**支持“技术上不是完全不可行”的证据：**

- 小规模 4v4 的完整 rollout P50 约 0.20 ms，单线程约 2.3M/s；clone 成本低于 1 µs（清 log 后）。这说明 MCTS 的原始吞吐并非天方夜谭。
- 1000 ms 预算约可跑 5k 次完整 rollout，足以在很小的遭遇战里做数百次根节点访问。

**反对“P7 默认采用 MCTS”的证据：**

1. **默认预算是 100 ms 量级。** 100 ms 只有约 500 次 rollout；300 ms 约 1.5k。对 8 combatant、7 轮、每回合多个候选动作/目标的树，这点样本不足以稳定区分动作价值。
2. **延迟。** 聊天/CLI 主持场景不适合每个 AI 决策固定花 0.3–1 s；P7 的目标是“质量可测的近似决策”，不是最强博弈。
3. **可复现性。** 若用 wall-clock 截断，行动排序会随机器负载变化；P7 AC-4 要求固定 seed/配置下可复现。MCTS 需要节点预算 + 固定 RNG 才能满足，这会进一步压缩可用样本。
4. **实现前置。** 当前没有单动作搜索 API、没有移动+动作原子 transition、没有重复状态管理；MCTS 会把这些缺口全部放大。应先有 A 的浅层基线。
5. **收益未证。** 现有启发式在合成测试中已能完成目标；没有证据表明 MCTS 在 P7 的预算内能稳定超过 UtilityPlanner。P7 明确不承诺 MCTS 级质量。

结论：**P7 不做 MCTS**；如果未来 P8 要做，先以本文的 rollout 预算为起点，在真实遭遇战上测 1k/5k/20k rollouts 的质量曲线，并用节点预算保证可复现。

## 7. P7 默认预算建议

建议 P7（Issue #176）采用以下默认值；这些是**建议**，最终由 P7 的实现与回归数据确认：

| 项 | 建议 |
|----|------|
| 搜索形状 | 方案 A：`ai.rs` 内 1 层动作/目标枚举；可选 2 层 top-K，对手只建模最佳回应 |
| 候选上限 | 每个决策最多 8–16 个根候选；2 层时 K ≤ 8；移动候选单独 top-K/航点 |
| 节点预算（主） | 256–512 个节点/决策（确定性、可复现） |
| 时间预算（安全阀） | 软上限 100 ms，硬上限 300 ms；超时立即回退 |
| 默认状态 | **默认关闭**；显式启用后才走 SearchPlanner，未启用时保持 UtilityPlanner/启发式 |
| 回退 | 预算耗尽、无合法候选、遇到未支持效果、搜索执行失败、真实 state 校验失败 → 回退 UtilityPlanner/现有启发式 |
| 日志 | 搜索 clone 使用 `NullSink`，clone 后立即清 log；禁止把整场 narration 带入搜索 |
| RNG | 每个搜索决策独立 seeded RNG；绝不消耗真实执行 RNG（P7 AC-1） |
| 证据 | 与 UtilityPlanner 对比质量、P50/P95 决策耗时、节点数、fallback 率、固定 seed 排序；不只报胜率 |

按本基准，256–512 个节点在 100 ms 内绰绰有余（动作级 10^3–10^4 节点），所以**真正的约束是候选质量与搜索语义，不是机器速度**。这也意味着 P7 不需要为了性能先做 B。

### 7.1 Fallback 条件（实现层）

- 真实遭遇战中单节点 P95 超过 50 µs，或 100 ms 内可用节点 < 32；
- 搜索深度需要 > 2 层才能产生与 UtilityPlanner 不同的决策；
- 出现无法在 clone 上安全结算的 effect/trigger/reaction；
- 搜索排序在固定 seed 下不稳定，或 fallback 率 > 10%；
- P7 回归显示 SearchPlanner 的胜率/目标达成没有统计上可辨的提升。

命中任一条件时，P7 应保持“默认关闭 + 浅层”或退回 UtilityPlanner，不得为了使用搜索而扩大 `engine.rs` 路径。

## 8. 限制与未验证假设

- **合成场景、单机数字。** 5 个动作/回合场景 + 1 个 4v4 rollout 只覆盖通用机制；真实内容的条件、触发器、reactions、更多 combatant、DM 裁定会改变常数。本文数字是量级参考，不是跨机器保证。
- **`NullSink` 是刻意选择。** step-mode 的 `Vec<String>` 日志会格式化并分配，成本显著高于本基准；搜索必须使用 `NullSink` 或等价物。
- **动作计时不含 clone。** 节点预算表已把 clone 加回；但候选生成、合法性检查、评分、重复状态检测仍未计入。
- **单回合 = 一个 actor 的 `take_turn`，不是一整轮所有 actor。** 回合级节点预算应按 actor 回合理解。
- **未测移动枚举、反应排序、真实内容加载。** 这些是 P7 的实现风险，不是本任务的测量结论。
- **未在 Windows/macOS 上跑。** 基准代码是跨平台的（CPU 型号探测有 cfg 分支），但本报告数字只代表上面这台 Linux 机器。
- **未验证“搜索一定改善决策质量”。** 本文只证明性能预算可行；质量必须由 P7 的合成对照与回归证明。

## 10. 对 P7 的直接引用建议

P7（Issue #176）在 READY 前应引用本文的以下结论：

- 动作级/回合级节点预算均为 10^3–10^4（100 ms），因此 1–2 层、top-K、默认关闭的搜索在现有引擎上可行；
- 不需要先改 `engine.rs`；方案 B 只在 §5.2 的触发条件下另开任务；
- clone 的主要成本是 log，搜索必须 `NullSink` + clone 后清 log；
- 默认预算建议 100 ms 软上限 / 300 ms 硬上限，节点预算 256–512 为主；
- P7 不采用 MCTS；若未来要做，先以真实遭遇战测 rollout 预算与质量曲线。
